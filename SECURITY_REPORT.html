📋 1. Resumo Executivo

O Sales MCP Server é um servidor MCP (Model Context Protocol) desenvolvido em .NET 8 que expõe ferramentas de análise de vendas (KPIs, relatórios, performance de vendedores) através de uma API HTTP com autenticação Bearer Token. A aplicação foi projetada com diversos controles de segurança desde sua concepção, demonstrando uma postura de security-by-design.

A análise identificou 6 vulnerabilidades (1 crítica, 1 alta, 2 médias, 2 baixas) em um universo de 12 controles de segurança verificados. O risco geral é classificado como MÉDIO, com as principais preocupações sendo a configuração de CORS permissiva em ambiente de desenvolvimento e a exposição de informações via endpoints anônimos.

Postura de Segurança 70%

🔑 2. Autenticação e Autorização

Mecanismo de Autenticação

A aplicação utiliza Bearer Token Authentication com esquema customizado (FileBearerAuthenticationHandler). O token esperado é lido de um arquivo em disco (BearerTokenFile), com cache thread-safe e detecção de alterações via FileSystemWatcher (last write time).

🔴 Endpoints de Diagnóstico Expõem Informações do Servidor ALTO
Arquivo: Sales.Mcp.Server/Endpoints/DiagnosticEndpoints.cs
Descrição: Os endpoints /health/live, /health/ready e /version são marcados com [AllowAnonymous]. O endpoint /version expõe o nome do assembly, versão e framework (.NET 8), informações que podem auxiliar um atacante a identificar versões vulneráveis.
Recomendação: Restringir o endpoint /version com autenticação ou removê-lo em produção. Para healthchecks, utilizar apenas /health/live e /health/ready, que expõem informações mínimas.

🌐 3. Segurança de Rede e Transporte

Validação de Origem (CORS)

O middleware OriginValidationMiddleware valida o header Origin das requisições ao endpoint /mcp. A validação é feita pelo AllowedOriginEvaluator, que normaliza a URI e compara com um conjunto de origens permitidas.

🔴 AllowedOrigins: "*" em Desenvolvimento CRÍTICO
Arquivo: Sales.Mcp.Server/appsettings.Development.json (linha 15)
Descrição: Em ambiente de desenvolvimento, AllowedOrigins está configurado como "*". Isso faz com que o AllowedOriginEvaluator trate o conjunto de origens como vazio (após split por vírgula, o valor "*" não é um wildcard válido), resultando em nenhuma validação de origem — qualquer site pode fazer requisições ao servidor MCP.
Recomendação: Substituir "*" pelas origens reais permitidas em desenvolvimento (ex: "http://localhost:6274,http://127.0.0.1:6274"). Considerar também implementar suporte a wildcard "*" no AllowedOriginEvaluator para maior clareza.
🟡 Ausência de HTTPS/TLS MÉDIO
Descrição: O servidor não possui configuração de HTTPS/TLS. O token Bearer e todos os dados trafegam em texto plano. Em produção, o container escuta em http://0.0.0.0:8080.
Recomendação: Configurar TLS no reverse proxy (nginx, Traefik) ou habilitar HTTPS no Kestrel com certificados gerenciados por Docker Secrets. Para ambientes internos com rede isolada, o risco é mitigado pelo port binding restrito.

🟡 Ausência de Rate Limiting MÉDIO
Descrição: Não há limite de requisições por cliente/IP. Um atacante pode fazer milhares de requisições simultâneas, potencialmente causando negação de serviço ou consumo excessivo de recursos do banco de dados.
Recomendação: Implementar rate limiting usando middleware ASP.NET Core (ex: AspNetCoreRateLimit ou System.Threading.RateLimiting). Configurar limites como 100 requisições/minuto por IP para endpoints MCP.
🟢 Ausência de Proteção contra Brute-Force BAIXO
Descrição: Não há mecanismo de bloqueio após múltiplas tentativas de autenticação com token inválido. Um atacante pode tentar adivinhar o token Bearer.
Recomendação: Implementar delay progressivo ou bloqueio temporário após N tentativas falhas de autenticação. O risco é mitigado pelo uso de tokens longos e aleatórios armazenados em arquivos seguros.

Análise de Vazamento de Dados

A aplicação expõe dados de vendas (faturamento, produtos, clientes, vendedores) através das ferramentas MCP. Todos os dados são consultados com uma conexão read-only usando o usuário mcp_reader, que possui apenas permissão de leitura no schema sales. Não há operações de escrita, exclusão ou alteração de dados.

Os DTOs de resposta expõem informações como nomes de clientes, códigos de vendedores, valores de comissão e métricas de performance. Embora sejam dados de um ambiente de demonstração (fake data), em produção é importante revisar se todos os campos são realmente necessários para o caso de uso.

🟢 Dados Sensíveis em Logs de Warning BAIXO
Arquivo: Sales.Mcp.Server/Middleware/OriginValidationMiddleware.cs (linha 40)
Descrição: O middleware registra a origem bloqueada no log de warning: _logger.LogWarning("Origem bloqueada. Origin={Origin} TraceId={TraceId}", ...). Embora não seja um dado crítico, a origem da requisição é registrada e pode conter informações sobre clientes ou sistemas internos.
Recomendação: Considerar mascarar ou truncar o valor de Origin nos logs, ou registrar apenas o TraceId para correlação. Em produção, configurar log aggregation com sanitização automática.

✅ 8. Recomendações e Plano de Ação

🔴 Imediatas (Críticas/Altas)

  • V-001: Corrigir AllowedOrigins no appsettings.Development.json — substituir "*" pelas origens reais. Estimar: 15 minutos.
  • V-002: Adicionar autenticação ao endpoint /version ou removê-lo em produção. Estimar: 30 minutos.

🟡 Curto Prazo (Médias)

  • V-003: Configurar TLS no reverse proxy ou habilitar HTTPS no Kestrel. Estimar: 2 horas.
  • V-004: Implementar rate limiting com System.Threading.RateLimiting (disponível no .NET 8). Estimar: 4 horas.

🟢 Médio Prazo (Baixas)

  • V-005: Adicionar contagem de tentativas falhas e delay/bloqueio temporário. Estimar: 3 horas.
  • V-006: Sanitizar logs ou remover Origin do warning. Estimar: 30 minutos.

📌 Boas Práticas Adicionais

  • Revisar DTOs de resposta para garantir que apenas dados necessários são expostos
  • Implementar auditoria de acesso (log de quais ferramentas foram chamadas e por quem)
  • Considerar criptografia em repouso (TDE) no SQL Server para dados de produção
  • Adicionar testes de segurança automatizados (SAST/DAST) no pipeline CI/CD
